# 6. RESULTS AND DISCUSSION

## 6.1 Experimental Setup

All experiments were conducted on a Windows 11 Pro machine using Python 3.12 in an isolated virtual environment. The FastAPI application was served locally via Uvicorn (ASGI mode), with MongoDB Atlas providing cloud-hosted document storage. The dataset used for training the AI price estimator consists of 545 rows generated by `scripts/generate_dataset.py`, which models the structure of the Kaggle "Housing Prices Dataset" (Yasser H.). Because the generator applies a fixed linear formula with Gaussian noise (numpy seed 42), the data do not represent real Indian property-market transactions — a significant caveat addressed throughout this chapter. The dataset was split 80/20 (random state 42), yielding 436 training rows and 109 test rows. Table 6.2 summarises the full experimental configuration.

[[TABLE Table 6.2 — Experimental setup.]]
| Parameter | Value |
|---|---|
| Python version | 3.12 |
| Web framework | FastAPI 0.111+ on Uvicorn (ASGI) |
| Database | MongoDB Atlas (shared/free tier) |
| ML library | scikit-learn (LinearRegression) |
| Dataset origin | Synthetic — generated by `scripts/generate_dataset.py` |
| Dataset rows | 545 (synthetic) |
| Training split | 80 % — 436 rows |
| Test split | 20 % — 109 rows |
| Random state | 42 (reproducible) |
| Baseline comparison | Custom CART regression tree (max_depth=5, min_samples_split=10) |
| Operating system | Windows 11 Pro 10.0.26200 |
| Image storage | Cloudinary (cloud CDN) |
| Evaluation metrics | R², MAE (₹), RMSE (₹) |

The custom CART implementation (`decision_tree.py`) served solely as a training-time baseline, necessitated because the host machine's Windows Defender Application Control (WDAC) policy blocked scikit-learn's compiled Cython tree extension during training. At inference time, only the serialised Linear Regression model (`model/model.pkl`) is loaded by the `/api/ml/predict` endpoint. Thirteen feature columns are used after one-hot encoding of `furnishingstatus` (dropping `furnished` as the reference category) and binary encoding of six yes/no fields [2].

## 6.2 Exploratory Data Analysis

Exploratory data analysis was performed in `notebook/house_price_training.ipynb` to understand the distributional properties of the synthetic dataset. Five charts were generated using **matplotlib** and **seaborn** [4][5].

[[EDA price_distribution.png | Figure 6.1 — Distribution of house prices (histogram + KDE).]]

Figure 6.1 shows a right-skewed price distribution with most synthetic records concentrated in the ₹40–60 lakh range and a long tail extending beyond ₹130 lakh. The skew is an artefact of the linear generation formula and chosen noise parameters rather than an empirical market observation. This distributional asymmetry is relevant to model evaluation because MAE and RMSE are sensitive to outlier predictions at the high-price tail.

[[EDA area_vs_price.png | Figure 6.2 — Built-up area vs price, coloured by furnishing status.]]

Figure 6.2 is a scatter plot of built-up area against price, coloured by furnishing status. A clear positive linear trend is visible — area is the dominant coefficient in the synthetic formula — and furnished properties command a slight premium at any given area, consistent with the binary premium encoded in the generator. The near-linear relationship is one reason linear regression achieves a moderate R² here; real-world prices are shaped by a far wider set of nonlinear factors not captured in this dataset.

[[EDA bedrooms_boxplot.png | Figure 6.3 — Price distribution by number of bedrooms.]]

Figure 6.3 presents box plots grouped by bedroom count. Median price rises progressively with bedrooms, and the IQR expands correspondingly, indicating greater variance for larger homes. Overlapping IQRs for adjacent bedroom counts (e.g., two- versus three-bedroom) confirm that bedrooms alone is an imperfect predictor; area and amenities provide stronger combined signal. This informed the decision to encode `bedrooms` as a numeric feature in the regression model, consistent with the strategy in `columns.pkl`.

[[EDA correlation_heatmap.png | Figure 6.4 — Correlation heatmap of numeric features.]]

Figure 6.4 shows a Pearson correlation heatmap of all numeric features. `area` has the strongest positive correlation with price (approximately 0.7–0.8), followed by `bathrooms`, `bedrooms`, and `stories`. Moderate cross-correlations exist among bedroom, bathroom, and storey counts, reflecting the realistic constraint that larger homes tend to have more of each. Binary amenity features show individually weaker correlations with price but collectively contribute additive increments. No predictor-to-predictor correlation exceeds 0.9, confirming the absence of severe multicollinearity and supporting stable OLS coefficient estimates [3].

[[EDA actual_vs_predicted.png | Figure 6.5 — Actual vs predicted price (Linear Regression & Decision Tree).]]

Figure 6.5 plots actual against predicted prices for both models on the 109-row test set, with a diagonal reference line representing a perfect predictor. Linear Regression clusters more tightly around the diagonal than the Decision Tree, confirming the quantitative advantage in Table 6.1. Both models show widening spread at high price values, indicating that neither captures premium-segment variance well. The CART tree's piecewise-constant predictions produce flat plateaus in the middle range, inflating absolute errors, while the linear model's smooth proportional relationship with actual values is unsurprising given the linear data-generating process [3].

## 6.3 Model Performance

Two models were trained and evaluated: scikit-learn's `LinearRegression` (OLS) and a custom CART regression tree (`decision_tree.py`, max_depth=5, min_samples_split=10). Table 6.1 reports metrics computed on the 109-row held-out test set. Linear Regression was selected for production deployment on all three metrics.

[[TABLE Table 6.1 — Model performance (test set, 109 rows).]]
| Metric | Linear Regression (selected) | Decision Tree (CART, baseline) |
|---|---|---|
| R² | 0.6538 | 0.4138 |
| MAE | ₹7,58,066 | ₹9,63,666 |
| RMSE | ₹9,39,058 | ₹12,21,894 |

The Linear Regression model achieves R²=**0.6538**, meaning approximately 65% of test-set price variance is explained by the thirteen input features. While a meaningful improvement over a naive mean predictor, 35% of variance remains unexplained — a modest result in absolute terms. The MAE of **₹7,58,066** (~₹7.6 lakh) is the average point-estimate error; the RMSE of **₹9,39,058** (~₹9.4 lakh) is higher, reflecting the disproportionate influence of large errors at extreme price points. The gap between MAE and RMSE is a measure of prediction inconsistency across the test set.

The Decision Tree baseline (R²=0.4138, MAE ₹9,63,666, RMSE ₹12,21,894) performs substantially worse. Its piecewise-constant nature at max_depth=5 prevents it from modelling the smooth linear relationship in the synthetic data [3].

**Honesty caveat — synthetic dataset:** These metrics must be interpreted with caution. Because the dataset was generated by a linear formula, a linear regression model is naturally expected to achieve a moderate R² — the model family is aligned with the data-generating process by construction. R²≈0.65 therefore does not validate usefulness on real Indian property data; it reflects how well OLS recovers the generating formula's parameters from a noisy 545-row sample. Genuine property prices are shaped by micro-location, infrastructure, developer reputation, negotiation dynamics, and market cycles — none of which are encoded in the thirteen features used here. The AI price estimator in NestQuest is accordingly an indicative guide, not a certified valuation. The application communicates this by displaying a ±8% confidence range (or ±RMSE, whichever is larger) around the point estimate [2].

## 6.4 Application Output

NestQuest was deployed and verified locally at `http://localhost:8000` via `python run.py` (Uvicorn with hot-reload). All server-rendered pages were exercised manually; annotated screenshots appear in Annexure B.

The home page (`/`) renders a hero section and a statistics banner populated from a live MongoDB aggregate. The property browser (`/properties`) accepts filter parameters — listing type, property type, city, locality, price range, bedroom count, furnishing, and area range — as URL query strings and returns paginated property cards from the `properties` collection, limited to `status=active` listings. Filtering is handled via server-side Jinja2 template logic with no JavaScript build step [10].

The property detail page (`/property/{id}`) displays a Cloudinary-hosted image carousel, owner contact information, and shortlisting or enquiry controls for authenticated users. The post-listing workflow (`/post`) uploads images to Cloudinary via a deferred `fetch` call to `/api/uploads/images` only on final submission, avoiding orphaned assets [11]. New listings receive `status=pending` and await admin approval.

The AI price estimator at `/insights` presents a form with twelve input fields corresponding to the thirteen model features. On submission, a POST request is sent to `/api/ml/predict`, which invokes `predict.py` and returns a JSON payload containing the predicted price and confidence interval, rendered inline via the `API` fetch wrapper in `app.js`. The admin panel (`/admin`) provides tabular views of all properties, users, and pending listings, with controls to approve, reject, or feature a listing.

## 6.5 Discussion

The results confirm that NestQuest meets its primary objective: a self-service, brokerage-free property marketplace with an integrated AI price estimator. All major modules — user authentication, property posting with image upload, faceted search, shortlisting, enquiry and reply, admin moderation, and ML-backed price estimation — were implemented and verified against the designed API surface.

**Brokerage elimination:** Property owners can post listings at no cost, and buyers contact owners directly, removing the intermediary entirely — the core value proposition [12][15].

**AI price estimator:** The estimator is functional end-to-end: from Jupyter training through model serialisation (`model.pkl`, `columns.pkl`, `metrics.json`) to the live `/api/ml/predict` endpoint. Predictions are logged to the `predictions` collection for future analytics. R²=0.6538 is satisfactory as a proof-of-concept on synthetic data but falls short of production-grade accuracy; replacing the synthetic dataset with verified Indian property transaction records augmented with location embeddings and temporal price indices could materially improve metrics [3].

**Security:** Password hashing with bcrypt (cost factor 12) [6], JWT-based session management with httpOnly cookies [7], and role-based access control via FastAPI's dependency injection are implemented. Two known gaps remain as future work: unescaped `$regex` user input (ReDoS/regex-injection surface) and absence of CSRF tokens on state-mutating form submissions [8].

**Architecture:** The FastAPI+Jinja2 server-rendered architecture delivers fast time-to-content without a JavaScript build pipeline, requiring only full-page round-trips for navigation. The Motor async driver keeps I/O-bound database operations off the Uvicorn event loop, providing acceptable concurrency within the free MongoDB Atlas tier [1][9].

**Honest ML limitations:** The synthetic dataset is the most significant caveat in this work. Because data were generated by a linear function, R²≈0.65 is best understood as a self-consistency check rather than a measure of generalisation to real data. The ±₹9.4 lakh RMSE is non-trivial relative to the median dataset price; buyers should treat estimator output as a ballpark guide. Future iterations should source real transaction data, explore non-linear models (Gradient Boosting, Random Forest), apply cross-validated hyperparameter selection, and incorporate features such as city tier, proximity to transport, builder reputation, and year of transaction [3].

In summary, NestQuest delivers a complete, deployable, full-stack web platform that meets its design goals within the constraints of a final-year academic project. The AI price estimator, while modest in predictive accuracy due to synthetic training data, demonstrates an end-to-end ML pipeline architecturally ready for improvement with real-world data without changes to the serving infrastructure.
